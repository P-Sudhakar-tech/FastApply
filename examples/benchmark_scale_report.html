The native fast path doesn't just beat pandas.apply() — it pulls away as data grows

Measured on this machine, median of repeated timed runs with warmup. Two cases route through a genuine native fast path under the default engine="auto": a numeric transform (x * 2 + 1) and a row-wise DataFrame function (row['a'] + row['b']). Both were originally benchmarked at 1,000 rows (~2x and ~4.5x). Scaled up to the range actually asked about here — 10,000 through 50,000 rows, then pushed further to find where it levels off — the gap widens well past 300%, because pandas.apply()'s per-row Python overhead grows linearly with row count while the native call barely grows at all.

Speedup vs. row count — and where the ceiling is

The requested range (10K–50K) sits right at core::PARALLEL_THRESHOLD = 50,000 elements — the point where the Rust core switches from a plain sequential loop to a rayon-parallel iterator. Pushing past it to 10M rows (numeric) and 500K rows (row-wise) shows the real shape of the curve: a dip right at the threshold crossing, then a climb to an asymptotic ceiling as pandas' linear per-row cost keeps growing against a near-flat native cost.

Methodology: time.perf_counter(), median of N repeats after warmup runs (repeats scale down as row count grows, since pandas.apply(axis=1) is slow enough at scale that a fixed high repeat count would dominate wall time). Numeric case repeats: 30 at 10K down to 3 at 10M. Row-wise case repeats: 30 at 10K down to 3 at 500K. Both cases verified correct against plain pandas on every run (turboply's sampling-based verification declines the native path rather than risk a silent mismatch).
